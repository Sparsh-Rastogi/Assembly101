## 1. Overview

An embedded system has a **central processor (CPU)** that must exchange data with **memory blocks** and **I/O devices**. Since these parts are built and clocked differently, we need well-defined techniques for moving data between them. The slides cover five:

| Technique | Core idea |
|---|---|
| Four-cycle handshake | Two devices coordinate a transfer using request/acknowledge signals, with no common clock needed |
| Microprocessor-mediated bus interfacing | CPU drives a shared bus (clock, R/W, address, data ready, data) to access memory and devices |
| Burst data transfer | Send one address, then move several data items back-to-back |
| Direct Memory Access (DMA) | A dedicated controller takes over the bus so the CPU is relieved of transfers |
| Cache controller | A small fast memory between CPU and main memory reduces average access time |

## 2. Four-Cycle Handshake

### 2.1 What it is
A **handshake** is a protocol that lets two devices (Device 1 and Device 2) synchronize a data transfer. It uses two control lines plus a data path:

- **Enq (Enquiry/Request)**: driven by Device 1 → Device 2
- **Ack (Acknowledge)**: driven by Device 2 → Device 1
- **DATA**: bidirectional data lines between the devices

```
 +----------+      Enq  ------->      +----------+
 | Device 1 |  <==== DATA ====>       | Device 2 |
 +----------+      <-------  Ack      +----------+
```

### 2.2 The four steps (cycles)
The signal diagram shows the two signals changing in a fixed order, each change **caused by** the previous one (the dashed arrows in the slide):

1. **Device 1 raises Enq**: "I want to transfer data."
2. **Device 2 raises Ack**: "I have seen your request and am ready." (This is caused by step 1.)
3. **Action phase**: the data transfer takes place while both signals are high (the grey "Action" region). Once finished, **Device 2 lowers Ack**.
4. **Device 1 lowers Enq**: it sees Ack drop, knows the transfer completed, and releases the request. (This is caused by step 3.)

Both signals are now back at their idle (low) state and the cycle can be repeated.

### 2.3 Why it matters
- Needs **no shared clock**; the devices wait on each other, so it works between fast and slow devices (asynchronous transfer).
- Each signal edge is an **acknowledgement of the previous one**, so neither device can get ahead of the other.
- It is called "four-cycle" because there are **four signal transitions**: Enq↑, Ack↑, Ack↓, Enq↓.

## 3. Microprocessor-Mediated Bus Interfacing

### 3.1 Architecture
The CPU, memory and I/O devices (Device 1, Device 2, ...) all connect to **one shared set of lines, the bus**. The CPU generates the address and controls the transfer; memory and devices respond.

```
CPU ──┬── Address enable
      ├── Clock
      ├── R/W
      ├── Address  (a bits)
      ├── Data ready
      └── Data     (n bits, bidirectional)
          │      │       │
       Device1  Device2  Memory   (all tapped onto the same lines)
```

Here **a** is the width of the address bus and **n** is the width of the data bus. The address bus size depends on the processor.

### 3.2 Signals and their roles

| Signal | Purpose |
|---|---|
| **Clock** | Provides time synchronization for all bus activity |
| **R/W** | Says whether the operation is a Read or a Write (relative to memory/I-O). Example convention: **HIGH = Read, LOW = Write** |
| **Address enable** | Indicates that a **valid address** is currently on the address bus |
| **Address bus** | Carries the address of the memory location or I/O device being accessed. Generated by the processor |
| **Data ready** | Indicates that **valid data** is available on the data bus so the read/write can be completed |
| **Data bus** | Carries data between the microprocessor and memory/I-O devices |

### 3.3 How a transfer proceeds (general idea)
1. CPU puts the **address** on the address bus and asserts **address enable**, with R/W set for read or write.
2. The addressed memory/device decodes the address and recognizes it is being selected.
3. When the data is valid, **data ready** is asserted and the data moves on the data bus (device → CPU for read, CPU → device for write).
4. CPU removes address enable/address, ending the transfer.

## 4. Bus Timing Diagrams

A **timing diagram** plots each signal against time (x-axis). Arrows between signals show **cause and effect** (which edge triggers which).

### 4.1 Read transfer
- **R/W is high** during the read.
- At a rising clock edge, **Address enable** goes high and the **Address** becomes valid. The address bus is drawn as a hexagon-like "bus" shape: lines may be at different values, but the whole bus is valid for that period.
- The addressed device responds: **Data ready** is asserted (drawn going low in the slide, i.e. active-low) and the **Data** becomes valid on the data bus.
- After the data is captured, Data ready returns high, then Address enable and Address are released.

### 4.2 Write transfer
- **R/W goes low** (write).
- CPU asserts **Address enable** and places the **Address** on the bus.
- CPU puts the **Data** on the data bus; Data ready indicates when it is valid so the memory/device can store it.
- Then the address and enable are released.

The slide shows a Read followed by a Write on the same time axis, with R/W switching from high to low between them.

### 4.3 Wait states
- If memory or a device is **slower** than the CPU, the data is not ready at the usual clock edge.
- The CPU inserts **wait state(s)**: extra clock cycles in which it simply waits (the grey region in the slide).
- Address enable has already been released, and **Data ready is asserted only later**, after which the data appears and the transfer completes.
- Wait states make the CPU compatible with slow peripherals, at the cost of **lower throughput** because each wait state wastes a clock cycle.

## 5. CPU Bus: Burst Data Transfer

### 5.1 Concept
In a normal transfer, **every data item needs its own address phase**. In a **burst transfer**, the CPU sends the address **once**, and then **several consecutive data items** (Data 1, Data 2, Data 3, Data 4) are transferred one after another, each in a clock cycle.

### 5.2 Signals
- A new control signal, **Burst**, is added.
- Burst stays **asserted (low in the slide)** while more transfers are coming and goes **high one transfer before the end**, i.e. it *signals until one final data transfer ahead*. This warns the device that the next item is the last.
- **Address enable/Address**: used only at the start (a single address).
- **Data ready** pulses once per data item, and **Data** shows Data 1 → Data 2 → Data 3 → Data 4.

### 5.3 Why use it
- Saves the **address overhead** for each item, giving **higher bandwidth**.
- Well suited to **cache line fills**, where several consecutive words from main memory are brought in together (the memory locations are consecutive).
- Memory devices (like DRAM) can supply consecutive locations quickly.

## 6. Direct Memory Access (DMA)

### 6.1 The problem
If the CPU moves every byte between I/O and memory itself, it spends much of its time just copying data and cannot do other computation.

### 6.2 The idea
A dedicated hardware module, the **DMA controller**, performs the data transfer between memory and I/O devices (or memory and memory) **without CPU involvement** for each word.

### 6.3 Bus request / bus grant
Only one master may drive the bus at a time, so control is handed over using two signals:

1. **Bus Request**: DMA controller → CPU: "I want the bus."
2. **Bus Grant**: CPU → DMA controller: "You may use the bus."

While the DMA controller owns the bus, it drives the address, R/W, and other control lines itself and transfers data between the device and memory. When finished, it releases the bus and the CPU takes over again.

### 6.3.1 Sequence
1. CPU programs the DMA controller (source, destination, length).
2. DMA controller asserts **Bus Request**.
3. CPU completes its current bus cycle, then asserts **Bus Grant**.
4. DMA controller performs the transfer.
5. DMA controller releases the bus; CPU resumes.

### 6.4 Advantages
- **CPU is relieved** of read/write transfer operations.
- CPU **bandwidth is saved** and can be used for other computation.
- Transfers can sometimes be **faster** when handled by the DMA controller than by the CPU.

## 7. Cache Controller Mediated Data Transfer

### 7.1 Block diagram
```
          Data
       ┌──────────  Cache
CPU ◄─►│ Cache      (small, fast)
       │ controller
       └──────────► Address ──► Main memory
                   ◄── Data ──  (large, slow)
```
The **cache controller** sits between the CPU and both memories. The CPU talks only to the controller; the controller checks the cache and, if needed, goes to main memory.

### 7.2 Key terms
- **Cache controller**: hardware that manages the cache and decides whether a request is served from cache or main memory.
- **Cache memory vs. main memory**: cache is small and fast; main memory is large and slow.
- **Access time**: using a cache **reduces average access time**, because most requests are served by the fast memory.
- **Working set**: the set of memory locations a program is actively using over a period. The cache is **much smaller than main memory**, so it works well only if the working set fits in it.
- **Cache hit**: the requested data is found in the cache (fast).
- **Cache miss**: the data is not in the cache, so it is fetched from main memory (slow) and typically placed in the cache.

### 7.3 Average access time (single level)
Let **h** = probability of a hit (hit rate), so the miss probability is **1 − h**.

$$t_{av} = h \cdot t_{cache} + (1-h)\cdot t_{main}$$

(The slide writes the hit rate as *b*; it is the same quantity as *h*.)

**Example:** t_cache = 2 ns, t_main = 50 ns, h = 0.9
t_av = 0.9×2 + 0.1×50 = 1.8 + 5 = **6.8 ns**, much better than 50 ns without a cache.

### 7.4 Multi-level caches
Modern systems use several levels: **CPU → L1 cache → L2 cache → Main memory**. Each level differs in:
- **Access time** (L1 fastest, then L2, then main memory)
- **Size / working set** (L1 smallest, L2 larger, main memory largest)

$$t_{av} = h_1 t_{L1} + h_2 t_{L2} + (1-h_1-h_2)\,t_{main}$$

(Written as b₁, b₂ in the slide.) Here **h₁** is the fraction of accesses that hit in L1, **h₂** the fraction that miss L1 but hit in L2, and **1 − h₁ − h₂** the fraction that go all the way to main memory.

**Example:** t_L1 = 1 ns, t_L2 = 10 ns, t_main = 100 ns, h₁ = 0.8, h₂ = 0.15
t_av = 0.8×1 + 0.15×10 + 0.05×100 = 0.8 + 1.5 + 5 = **7.3 ns**.

## 8. Quick Comparison Table

| Feature | Four-cycle handshake | Normal bus transfer | Burst transfer | DMA | Cache |
|---|---|---|---|---|---|
| Who controls transfer | Two devices peer-to-peer | CPU | CPU | DMA controller | Cache controller |
| Needs clock | No | Yes | Yes | Yes | Yes |
| Address per data item | n/a | Yes | No, one address for the whole burst | Handled by DMA | n/a |
| Main benefit | Safe asynchronous sync | Simple, general | Higher bandwidth | Frees CPU | Lower average access time |
